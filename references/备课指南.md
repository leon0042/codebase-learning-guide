# 备课指南：如何在零背景的前提下读懂一个陌生项目

第 0 步的详细方法。目标不是"读完项目"，而是**建立一份够用的地图**，让后续每一句讲解都有据可查。

判据很朴素：**学生拿这份地图，能自己找到任何一个功能的代码位置。**

## 时间尺度与投入分配

一份够用的地图，小项目（几千行）约 10–20 次工具调用，中大项目（几万行以上）约 30–50 次。**不要在备课上无限投入**——备课是为了开口，不是为了自己先精通。学生等着的是第一句话，不是你读完所有代码。

经验分配：

| 环节 | 占比 | 说明 |
|---|---|---|
| 机械扫描 | 5% | 一个脚本调用 |
| 读文档与清单 | 25% | 性价比最高，项目自己的陈述 |
| 追主链路 | 50% | 大部分时间在这里，这是地图的骨架 |
| 写地图 | 20% | 写下来才算备课完成 |

## 步骤一：机械扫描

```bash
python scripts/project_scan.py <项目根> --top 20
```

输出是一个 JSON，重点看五个字段：

| 字段 | 用来回答的问题 |
|---|---|
| `summary.top_languages` | 主语言是什么？是单语言还是混合？ |
| `directory_tree` | 顶层怎么划分的？哪个目录像核心？ |
| `build_and_dependency_manifests` | 用什么构建、依赖什么、怎么跑？ |
| `entry_point_candidates` | 程序从哪进？ |
| `largest_source_files` | 哪些文件最重？通常就是要点所在 |

另外 `git.recently_changed_top_level`（若在 git 仓库内）告诉你**开发热点**——最近改动最频繁的目录往往是项目当前的重心，也是学生最该先读懂的地方。

### 先算清"项目自己有多少代码"

**这是拿到新项目时最容易犯的错：把第三方库当成项目规模。** 一个实际 1.8 万行的工程，扫描可能报 37 万行——因为 `lib/` 下躺着 Eigen、MAVLink、FreeRTOS 这类 vendor 树。差 20 倍，会直接毁掉你对"这项目多大、要学多久"的判断。

看两个字段交叉判断：

1. `largest_top_level_dirs` —— 哪个顶层目录的文件数压倒性地多？
2. 读该目录里的构建文件或许可证（`CMakeLists.txt`、`LICENSE`、`README`）——它是**项目自己的代码**还是**照搬进来的库**？

判据：**该目录下有没有你自己项目写的业务逻辑？** 没有就是 vendor。

确认是 vendor 后用 `--exclude` 重扫，得到真实规模：

```bash
python scripts/project_scan.py <项目根> --exclude lib,vendor,third_party --top 20
```

`skipped_top_level_dirs` 字段列出所有被跳过的顶层目录（备份、构建产物、依赖缓存）。**它是空的时候也要看一眼**——如果里面有你需要的目录，说明扫描漏了它，得用 `--exclude` 调参重扫或直接手工读。

vendor 目录本身是**真实存在的依赖**，要在项目地图里记一行（"依赖 Eigen（`lib/eigen/`）做矩阵运算"），只是不要把它算成学习负担——学生几乎永远不需要读 vendor 源码。

**扫描结果只是候选，不是结论。** 脚本按文件名和扩展名猜，猜错很正常（比如 `main.py` 是废弃的旧入口）。凡是地图里要写进去的，都得打开确认一眼。

### 输出太大怎么办

`--top 5 --max-depth 1` 先看全局，需要时再放大重跑。脚本输出会进上下文，没必要一次拉全部。

## 步骤二：读文档

按这个顺序读，**读完一条就判断够不够，够了就停**：

1. **项目级 agent 说明**（`AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING.md`）——这里面通常是硬性约束、命令、踩坑记录。这是全项目信号密度最高的文件，如果存在必读。
2. **`README`**——项目自称是什么、怎么跑、有哪些模块。
3. **`docs/` 的索引文件**（不是全部文档）——看目录结构，知道有哪些主题的文档可用；具体内容等学生要学那一块时再读。
4. **架构 / 设计文档**（`ARCHITECTURE.md`、`docs/design/*`）——如果存在，直接给你模块划分。

### 读文档的纪律

**代码与文档冲突时，一律以代码为准。** 文档描述的是"项目打算成为什么"，代码是"它现在是什么"。这两者经常不一致，而且不一致本身往往就是学生最容易踩的坑——如果你发现了，明确指出，这是高价值信息。

## 步骤三：读构建清单

不同技术栈要读的东西不同，但目的统一：**知道这个项目怎么被构建、怎么被运行、依赖了哪些外部东西。**

| 技术栈 | 读什么 | 能得到什么 |
|---|---|---|
| Node / 前端 | `package.json` | `scripts` 里的命令、`main`/`bin` 入口、依赖列表 |
| Python | `pyproject.toml` / `requirements.txt` / `setup.py` | 包结构、入口点（`[project.scripts]`）、依赖 |
| Rust | `Cargo.toml` | `[[bin]]` / `[lib]` 目标、工作区成员、依赖 |
| Go | `go.mod` | 模块名（决定 import 路径）、依赖 |
| Java / Kotlin | `pom.xml` / `build.gradle` | 模块划分、主类、依赖 |
| C / C++ | `CMakeLists.txt` / `Makefile` | 目标（target）、源码集合、链接库 |
| 嵌入式 | `platformio.ini` / `west.yml` / `Kconfig` | 目标板、构建环境、开关选项 |
| .NET | `*.csproj` / `*.sln` | 项目划分、目标框架、启动项目 |

构建清单里的**依赖列表**顺带告诉你这个项目跑在什么抽象层上——比如看到 `px4_msgs`、`FreeRTOS-Kernel`、`React`、`ros2`，你就大概知道它的架构风格了。

## 步骤四：追一条主链路

**这是备课的核心动作，也是地图的骨架。** 前面三步得到的是静态结构，只有追完一条链路，你才知道这些模块是怎么串起来的。

### 怎么选链路

选**最有代表性**的一条——它能带你穿过大多数核心模块。按项目类型：

| 项目类型 | 追什么 |
|---|---|
| Web 服务 | 一个 HTTP 请求：路由注册 → 中间件 → 业务处理 → 数据库 → 响应 |
| 前端应用 | 应用挂载 → 根组件 → 一个页面的数据获取与渲染 |
| CLI 工具 | 一条命令：参数解析 → 命令分发 → 核心逻辑 → 输出 |
| 嵌入式 / 固件 | 一个控制周期或一次中断：采样 → 解算 → 控制 → 输出 |
| 库 / SDK | 一个最常用的公开 API：从调用到返回 |
| 数据处理 | 一份输入数据：读取 → 清洗 → 变换 → 写出 |
| 编译器 / 解释器 | 一段源码：词法 → 语法 → 中间表示 → 执行或生成 |

### 怎么追

1. 从入口文件开始，`Read` 第一屏（约 100–200 行），**不要一次读完整个文件**。
2. 找出它调用的第一个"非本次读取范围内的"函数，跳到那个定义。
3. 重复。每一步记下 `文件:行号 和一句话职责`。
4. 追到"出结果"为止（响应发出 / 数据写入 / PWM 输出 / 返回值）。

### 追到什么程度算够

**够的标准是：你能用一句话说清这条链路上每个环节干了什么。** 不需要看懂每个函数的内部实现——那是第 5 关的事。备课阶段只需要知道"这里有一个做 X 的环节，在 A 文件"。

### 用 grep 补跳转

在大型项目里，从调用点到定义往往不是相邻的两行。用搜索比翻文件快得多：

```bash
# 找函数定义（按语言调整模式）
grep -rn "def function_name\|function_name *=\|function_name(" --include=*.py .
```

找不到定义时，考虑：它在依赖库里（去看构建清单）、它是生成的代码、它是宏/元编程展开的、或者你搜错了名字。**这四种情况都要向学生说明**，它们是初学者最常卡住的地方。

## 特殊规模项目怎么办

### 项目没有可执行代码（纯文档 / 提示词 / 配置型）

有些文件夹根本不是程序：提示词库、技能包、配置仓库、规范文档集、模板集。扫描会给出"语言分布几乎全是 Markdown、入口候选为空、构建清单为空"。

**这时不要套用代码项目的路线**，换成按下面的方式备课：

| 代码项目 | 文档型项目对应 |
|---|---|
| 入口文件 | **事实源**：哪一个文件是被真正读取/执行的（如 `SKILL.md`、`main.yaml`、`index.md`） |
| 调用链 | **引用关系**：谁引用了谁——`[[链接]]`、`include`、markdown 相对链接、模板变量 |
| 模块职责 | **每份文档负责什么、何时被读** |
| 数据结构 | **贯穿全局的约定**：命名规范、字段含义、格式模板 |
| 主链路 | **一次使用的时序**：从使用者发起 → 读哪个文件 → 按什么顺序用哪些资源 → 产出什么 |

后四节的六关照用，只是判据换说法：第 2 关"能说出哪些文件是主干、哪些按需加载"，第 4 关"能说出一次完整使用经过哪些文件"。**第 6 关尤其适合这类项目**——写一个符合该约定的新条目，是最直接的验证。

扫描脚本对这类项目能力有限（它按源码扩展名统计），**以手工读文件为准**，别因为脚本说"没什么内容"就以为项目很小。

### 项目很大（首屏读不完）

不要试图通读。改用**分片备课**：

1. 只对当前要教的那一块做完整备课（比如"先学通信层"就只追通信那条链路）。
2. 地图先写顶层结构 + 一个"待探索区域"清单，明确标注哪些部分还没看。
3. 学生推进到新区域时，再做那一片的局部备课。

**绝不要假装自己读过没读过的部分。** 地图上标 `待确认` 比编一个看起来完整的描述强一百倍。

### 项目很小（一两个文件）

跳过模块划分那部分，重点放在：

- 这个文件解决什么问题
- 数据结构是什么形状
- 主流程怎么走
- 有哪些边界条件处理

小项目照样有六关，只是每关的颗粒度更细（关卡 2 可能变成"这一个文件里的函数分组"）。

### 项目是生成/混淆过的，或几乎没有可读源码

如实告诉学生：这个项目不适合以"读懂源码"为目标的入门学习，说明原因（代码生成、混淆、只有二进制），并给出替代路线（读文档、读类型定义、读测试用例、读配置）。**不要硬凑一份假地图。**

## 自检清单

写完 `project-map.md` 后逐条自问，任一为否就回去补：

- [ ] 我能说出这个项目解决什么问题，且不是直接抄 README 的第一句
- [ ] 每个顶层目录我都知道它负责什么，且指向真实路径
- [ ] 我知道程序从哪启动，并能指出具体文件
- [ ] 我追通了一条主链路，链路上的每个环节都有 `文件:行号`
- [ ] 我能列出五个值得深挖的点，且每个都有理由
- [ ] 地图里所有 `待确认` 的地方都真的标了，没有用模糊表述蒙过去
- [ ] 学生拿这份地图能自己找到"改某个行为要动哪里"
- [ ] 如果发现了文档与代码冲突，已记入地图第八节
- [ ] 如果这是文档型项目，"事实源"和"引用关系"已替代"入口"和"调用链"填好

## 常见坑

- **只读 README 就开讲。** README 是营销文案加快速上手，不含真实结构。必须落到代码。
- **先翻目录不跑扫描。** 手工翻目录会漏掉隐藏目录、会高估小文件的重要性、还会烧掉大量工具调用。
- **一次追三条链路。** 会得到三份半成品，谁都不像。
- **在一处细节上陷进去。** 备课阶段看到一段精妙实现，读懂它花了 20 次调用——这是过拟合。记进"值得深挖的点"，等第 5 关再回来。
- **把编译产物当源码。** `build/`、`dist/`、`node_modules/`、`.pio/` 里的东西不是项目逻辑。扫描脚本已跳过常见目录，手工翻的时候也要留意。
- **地图写成散文。** 地图的作用是查，不是读。表格 + `文件:行号` 优先。
- **忘了看 git 历史。** 最近的提交信息常常直接说明"这个项目现在在长什么"，比任何文档都新。
