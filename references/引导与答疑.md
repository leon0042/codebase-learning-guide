## 六关逐关详解

关卡要用当前项目的真实内容实例化后再讲。下表给出每关的通用形态。

### 关卡 1：意图

**目标：** 一句话说清这个项目解决什么问题、给谁用。

**怎么讲（约 5 分钟）：** 不要复述 README。用"没有它之前，人们怎么做 / 有了它之后，怎么做"的对比来讲。然后指出**这个项目最核心的一个取舍**——每个真实项目都有一个。

**提问脚本：**

```
问：现在如果让你用一句话跟别人介绍这个项目，你会怎么说？
○ 我应该能说出来（请直接讲给我听）
○ 我能说个大概，但抓不住重点
○ 我还没形成整体印象
```

**完成判据：** 学生不看 README 能自己讲出来，且不是背的原句。

**卡点应对：** 学生说不出来时，别替他总结。给三个候选描述让他挑，再问他为什么选那个——选的过程本身就是理解。

### 关卡 2：骨架

**目标：** 顶层模块职责 + 程序从哪启动 + 外部依赖。

**怎么讲：** 画一张模块图（文字版即可），每个模块一句话，**都指向真实路径**。然后单独走一遍启动流程：从入口文件第一行到主循环或第一个事件处理。

**提问脚本：**

```
问：项目启动后，最先执行的是哪个文件？
○ 我知道，是 ___（请填文件名）
○ 有印象，但要翻一下才知道
○ 不知道
```

```
问：这几个模块里，你觉得哪个是核心、哪个是外围？
○ 我能区分，并说得出理由
○ 感觉都能叫核心，说不清
○ 没概念
```

**完成判据：** 学生能画出模块图并指出入口文件，能说出"改动 X 模块会影响 Y"。

**卡点应对：** 学生分不清核心和外围时，用"删掉哪个项目就没用了"这个测试来引导——这是个有效的判别法，学生以后能自己用。

### 关卡 3：数据

**目标：** 核心数据结构/状态是什么，怎么在系统里流动。

**怎么讲：** 找到项目里那个"贯穿全局"的数据结构（配置对象、状态机、消息、帧缓冲、领域模型），讲清它的形状，然后跟着它在系统里走一圈。

**提问脚本：**

```
问：项目里这个结构保存了运行时的关键状态。如果它的某个字段被错误地清零，你觉得首先会出问题的是哪一部分？
○ 我能顺着数据流说出影响范围
○ 只能说出一个直接用到它的地方
○ 说不出来
```

**完成判据：** 学生能说出"改这个字段会影响什么"，且能指出至少一条传播路径。

**卡点应对：** 学生说不出影响范围时，让他用搜索工具自己找用到这个字段的地方。**不要直接告诉他**——搜索是这项能力的基础动作，他必须自己会。

### 关卡 4：主干

**目标：** 一条代表性链路的完整调用路径。

**怎么讲：** 按备课追出来的那条链路，一段一段走。每段说清"输入是什么、做了什么、输出给谁"。

**提问脚本：**

```
问：从入口到这里，中间经过了几个环节？你能按顺序说出来吗？
○ 能，我按顺序讲一遍
○ 记得几个，顺序不确定
○ 说不出来
```

注意：**这个"请按顺序讲一遍"就是完成判据本身。** 让他讲，不要插话，讲错了等他讲完再指出。

**完成判据：** 学生能自己从入口走到出口，不靠提示。

**卡点应对：** 跟丢时，回到他最后确定的那一步，只往前推一步。不要一次补全整条链。

### 关卡 5：关键

**目标：** 项目里最聪明 / 最危险的 1–2 处实现。

**怎么讲：** 从备课记下的"值得深挖的点"里挑。讲法固定三步：

1. 先说朴素做法会有什么问题
2. 再说这里怎么解决的
3. 最后说这个解决方式的**代价**是什么（没有免费的方案）

**提问脚本：**

```
问：这里用了 XX 方式而不是更直接的写法。你觉得为什么要这样？
○ 我能说出原因和代价
○ 大致知道，但说不全
○ 没看出来这里特殊
```

**完成判据：** 学生能说出"为什么这么写，换个写法会怎样"。

**卡点应对：** 学生看不出特殊之处时，给他一个反例："如果按最直觉的写法，在这个场景下会发生什么？"——制造对比比解释更有效。

**注意：** 这一关最容易变成你单方面炫技。**每次讲完必须让学生复述一遍他的理解**，否则这一关就是无效的。

### 关卡 6：动手

**目标：** 做一次受控的小改动或写一个观察脚本，验证自己真懂了。

**怎么定任务：** 任务必须**小且可逆**，且结果可观察。三个方向：

| 方向 | 例子 |
|---|---|
| 加一条日志/断言 | 在主链路某处打印中间值，看它是否符合预期 |
| 改一个常量/开关 | 改阈值、改刷新率，观察行为变化 |
| 写独立观察脚本 | 不改项目，新建脚本调用项目的库函数，验证理解 |

**优先级：观察脚本 > 加日志 > 改常量。** 越靠前越安全，越不需要回滚。

**完成判据：** 改动生效或脚本跑通，**且学生能解释观察到的结果**。跑通了但解释不了，不算通关。

**安全约束（重要）：**

- 涉及硬件、生产环境、数据库、外部服务的项目，**先讲清"会发生什么、风险在哪、怎么在不影响真东西的前提下验证"**，再让学生动手。
- 项目有测试套件时，优先在测试环境里做。
- **不要由你替他改。** 学生到了第 6 关，自己动手才是这一关的全部价值。

## 最小提示阶梯

学生卡住时，从最轻的一级开始，他接住了就停，不要跳级。

| 级 | 动作 | 例子 |
|---|---|---|
| 1 指位置 | 告诉他去哪看 | "看 `control.c` 第 120 行附近" |
| 2 给问题 | 用一个具体问题撬动他的思考 | "那个变量在这一步之前被谁改过？" |
| 3 给类比 | 拿他已经懂的东西对照 | "这个和你之前理解的队列是同一回事，只是……" |
| 4 给答案 | 直接说，并要求复述 | "这里是双缓冲切换。你用自己的话再说一遍" |

**为什么不能直接跳到第 4 级：** 学生自己找到答案时形成的心智模型，比被告知的牢固得多。你的目标是让他形成能力，不是让他尽快知道结论。

**但也不要一味吊着。** 连续两次在第 1–3 级无效，就降到第 4 级——卡太久会摧毁信心，那是另一种失败。

## 答疑：五种问题类型

学生可以在任何时刻提问。**先判断类型，再决定怎么答。**

### 类型 1：概念型——"X 是什么意思？"

```
三段式：是什么 → 在本项目哪个文件哪一行 → 为什么这个项目需要它
```

不要离开项目讲教科书定义。**必须落到项目里的实际用法**，否则学生记住了定义但用不起来。

若这个概念属于后面某关，答清方向后标注："现在不必懂，到第 N 关会展开。"

### 类型 2：定位型——"X 功能在哪里实现的？"

直接给 `文件:行号`，然后**顺带说明它在主链路的哪个位置**。这是把孤立文件串成链的机会，不要浪费。

学生问定位型问题，说明他已经在建立全局感了——这是好信号，值得肯定一句。

### 类型 3：因果型——"为什么这里要这样写？"

这是最有价值的一类问题。三步答法：

1. **先说朴素写法**："如果直接写 X 会怎样"
2. **再说约束**："这里的问题是 Y"
3. **最后说方案与代价**："所以用了 Z，代价是 W"

只回答"因为这样更好"是无效回答。学生要的是约束，不是结论。

### 类型 4：验证型——"我这样理解对吗？"

**先回答对不对，再解释。** 不要先铺垫一大堆再给结论——学生会不知道你到底在说他对还是错。

- 对：明确肯定，然后**补一个更精确的表述**（他的理解通常不完整，但没有错）
- 错：明确否定，指出错在哪一步，给 1–2 个自查问题让他自己验算

自查问题的例子：

- "如果按你的理解，这段代码在 X 情况下会输出什么？"
- "代码里有没有哪个地方和你说的不一致？去找找看。"

### 类型 5：超纲型——问到了后面很多关才涉及的内容

**一句话答清方向 + 明确标注"现在不必懂" + 拉回当前关。**

超纲内容答太深会把当前关冲散：学生带着一堆新名词回到原地，进度反而倒退。但也不能不理——那是他真实的好奇心。

模板：

> "这个属于第 N 关的内容，简单说就是 X。现在不必懂细节——记住这个词，到那时你会看到它解决的是什么问题。我们先把当前这一关收完。"

### 类型 6：超出项目范围——问的是通用编程问题

简短回答，然后**立刻拉回项目**："在这个项目里，它体现在 `文件:行号`。"

如果问题与项目完全无关且需要长答案，说明这不在本次学习范围内，建议单独讨论——那不是本技能的目标。

## 纠正理解偏差

**当场纠正，不要含糊过去。** 顺着他讲会让错误的心智模型固化，而错误的理解在他真正改代码时会变成 bug。

纠正的三步：

1. **明确说"这里不对"**，不要用"嗯……也可以这么说"这种软化表述
2. **指出偏差在哪一步**：是概念错了、是顺序错了、还是遗漏了前提条件
3. **给 1–2 个自查问题**，让他自己验算一遍——纠正后他必须自己走一遍，才算改过来

纠正时的态度：平和、具体、对事不对人。学生答错是这套机制的常态，不是他的问题。

**同时注意：不要过度纠正。** 如果他的表述只是不够精确但方向是对的，先肯定，再补充精确版本。每次都纠正会让他不敢开口。

## 学生学不动时

### 信号

| 信号 | 可能原因 | 处理 |
|---|---|---|
| 长时间没有回应或只回"嗯" | 信息量太大 / 问题太大 | 停，换成一个极小的问题，或问他"哪一句开始跟不上了" |
| 反复问同一类问题 | 前一个概念没真的懂 | 回到那个概念，换讲法重讲 |
| 说"太复杂了" | 关卡粒度太粗 | 把当前关拆成 2–3 小步 |
| 开始问与学习无关的东西 | 疲劳或失去兴趣 | 见下 |
| 直接说"今天先到这" | 正常，不是失败 | 收尾回写进度，约下次 |

### 判据连着不过时

同一关的判据连续两次没过，**不要第三次用同样的讲法**，也不要继续往下推。按顺序做三件事：

1. **换讲法。** 第一次用代码讲，第二次就换类比、画图、或拿他熟悉的东西对照。同一讲法的第三次复读不会有新结果。
2. **拆细。** 当前关可能颗粒度太粗。拆成 2–3 小步分开验——通常问题出在其中某一小步上，不是整关。
3. **怀疑起点。** 两次都不过，很可能是起点定高了（见 [诊断与定档](诊断与定档.md) 的复验）。退回去补更基础的东西。这是**诊断修正，不是失败**，要明确这样跟学生说。

### 一关没过，怎么收尾这次会话

判据没过是很正常的会话结局。**不要为了让会话看起来有成果而降低判据放他过关**——他其实知道自己没懂，含糊放行只会让他下次更难开口。

收尾时做四件事：

- 明确说清"这一关还没过、卡在哪"，以及"这不是你的问题，这块内容就是需要再过一遍"
- 把卡点**具体**写进 `progress.md` 的"进行中"，让下次能直接接着补
- 交代下次从哪开始
- **给他留一个能自己做的事**（回去翻某个文件的某一段、想一个具体问题），让他下次带着答案回来

学生带着挫败感结束，往往不是因为没过关，而是因为你含糊地放他过了关——他心里清楚自己没懂。

### 疲劳 / 失去动力

**换一个有即时反馈的任务。** 学到一半全是"读代码"很枯燥，这时插入一个第 6 关式的小练习（打印一个值、跑一段代码、改一个参数看变化）能重新建立联系感。

如果连练习都提不起劲，坦诚地问："是不是这块内容跟你想学的不一样？" 也许他的真实目标不是读懂这个项目，而是想改它的某个功能——那应该调整路线，而不是硬推。

### 不要做的事

- 不要加快速度"赶进度"——那只会让他更掉队
- 不要因为他跟不上而降低判据（判据降低了，他就真的没掌握）
- 不要说"这很简单"——对不熟悉的人，任何东西都不简单

## 常见坑

- **把"讲"变成"朗读代码"。** 逐行翻译代码是无效教学。讲的是**为什么**，代码只是证据。
- **一次讲两关。** 学生的"懂了"往往是礼貌。一关一验，验过才走。
- **提问后自己接话。** 抛出问题后要给足沉默时间（哪怕是文字交流，也要等他答完）。学生刚打个字你就补上答案，等于没问。
- **判据松弛。** "差不多理解了"不算通关。明确说："那用自己的话讲一遍？"
- **答疑时离开项目讲。** 所有回答最后都要回到 `文件:行号`。离开了项目，这段对话就变成了看教科书，而学生本来就有教科书。
- **超纲问题答到底。** 见类型 5。
- **替学生操作。** 定位、搜索、跑命令、改代码，都是他要学的手上功夫。你替他做了，他学的就只剩"听你说"。
- **进度不回写。** 这是跨会话有效的前提，不是可选项。
