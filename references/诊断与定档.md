## 四个诊断维度

不管什么项目，"能不能学下去"取决于四件事。缺哪一件，学生就会在那个位置卡住：

| 维度 | 问的是什么 | 卡住的表现 |
|---|---|---|
| **D1 语言与惯用法** | 项目主语言的基础语法、惯用写法、标准库 | 读得懂英文单词，读不懂代码在干什么 |
| **D2 工具链** | 编译/构建、运行、调试、依赖管理、版本控制 | 想验证自己的理解，但跑不起来 |
| **D3 领域知识** | 这个项目解决的问题所属领域的概念 | 每个字都认识，但不知道为什么要这么做 |
| **D4 代码阅读能力** | 多文件架构、抽象层次、异步与并发、测试 | 单个函数看得懂，连起来就晕 |

D1 和 D2 是**硬门槛**：不会就没有继续的可能，必须先补。
D3 是**软门槛**：可以边学边补，但要在相应关卡放慢。
D4 是**本技能要训练的能力本身**：不需要先具备，但需要知道起点在哪，好决定要不要把每关拆得更细。

## 出题四步法

### 第一步：从项目地图里挑知识点

对着 `project-map.md` 问自己：**这个项目里，哪个知识不具备就完全读不下去？**

例如：

| 项目 | 决定性的知识 | 维度 |
|---|---|---|
| STM32 飞控固件 | C 语言指针与结构体、寄存器/外设概念、PID 与姿态解算 | D1、D3 |
| React 前端 | JS/TS 语法、组件与状态、异步与渲染时序 | D1、D4 |
| Python 数据处理 | Python 语法、pandas/NumPy 用法、领域统计概念 | D1、D3 |
| ROS2 机器人 | C++ 或 Python、ROS2 通信模型、坐标系变换 | D1、D3 |
| Rust 系统工具 | 所有权与生命周期、Cargo、并发 | D1、D2 |

### 第二步：每个维度问一题，问最可能卡住的地方

**一题只问一个知识点**，不要问"你懂 C 语言和硬件吗"这种一题两问。

**优先问最可能是瓶颈的那一项**，而不是全问一遍。典型判断依据：

- 项目主语言小众（Haskell、Verilog、Ada）→ 优先问 D1
- 项目构建复杂（交叉编译、多个子模块）→ 优先问 D2
- 领域高度专业（飞控、编译器、金融风控）→ 优先问 D3
- 项目架构抽象（事件驱动、插件化、多进程）→ 优先问 D4

### 第三步：把知识点翻译成行为化的选项

见下节[选项设计规范](#选项设计规范)。

### 第四步：一次不超过 4 题

结构化提问工具通常一次最多 4 个问题。**不要为了问完 4 个维度就把所有问题挤进去**——学生答完 4 题已经很配合了。最相关的前 3–4 题先问，剩下的看后面的交流自然补上。

## 各维度示例题

以下只是**写法示范**，不是题库。实际题目必须换成当前项目的具体技术。

### D1 语言与惯用法

```
问：这个项目主要用 C++。你目前对 C++ 的掌握程度是？
○ 完全没学过
○ 学过基础语法，但没写过完整程序
○ 能看懂别人写的类与模板代码
○ 能自己写，包括 STL 和现代特性
```

```
问：这个项目用 Python 的类型注解和 dataclass 组织数据结构。这类写法你熟悉吗？
○ 没接触过类型注解
○ 见过，但不确定自己能不能读懂
○ 能读懂，自己写的时候不太用
○ 熟悉，日常就这么写
```

### D2 工具链

```
问：要从源码跑起这个项目，需要自己编译。你的经验是？
○ 从没编译过别人的项目
○ 跟着教程跑通过，但出错不会查
○ 能独立编译并解决常见报错
○ 熟悉构建系统，能改构建配置
```

```
问：这个项目用 git 管理，你要读的代码经常需要看"这行是谁改的、为什么改"。你用过 git 吗？
○ 没用过
○ 会 clone、pull，别的不会
○ 会看提交历史、diff、切分支
○ 能做 rebase、查 blame、二分定位问题
```

### D3 领域知识

```
问：这个飞控工程里的"姿态解算"和"推力矢量"，你之前接触过吗？
○ 完全没概念
○ 听说过名词，说不清具体是什么
○ 懂原理，但没实际接触过工程实现
○ 做过相关的项目或课程设计
```

```
问：这个后端项目围绕"事件溯源 + 最终一致性"组织。这类架构你了解吗？
○ 没听说过
○ 知道概念，说不清为什么这么用
○ 理解原理，能说出取舍
○ 实际项目里用过
```

### D4 代码阅读能力（这个维度问的是经验，不是知识）

```
问：你之前读过多少行数的别人写的代码？
○ 基本没读过，只看自己写的
○ 读过几百行的单文件项目
○ 读过上万行的多模块项目
○ 经常读陌生代码库并给别人讲
```

```
问：这个项目里异步和回调用得比较多。读这类"跳来跳去"的代码，你之前有过经验吗？
○ 没读过，感觉很乱
○ 读过一点，容易跟丢
○ 能跟上，但需要画图辅助
○ 比较习惯，能在脑子里追调用链
```

## 选项设计规范

**按能力阶梯排列，不按对错排列。** 学生选任何一项都不是"错"，只是描述位置。

四档的标准形态（对应"能不能学下去"的不同对策）：

| 档 | 语义 | 对策 |
|---|---|---|
| 1 | 完全没接触过 | 必须先补，插入前置内容 |
| 2 | 听说过 / 跟着做过 / 能看懂别人的 | 可以在引导中带过，配示例 |
| 3 | 能独立完成 | 直接进关，但要多做验证 |
| 4 | 能给别人讲清楚 / 改造过 | 可以直接跳关，或者反过来请他讲给你听 |

其他要点：

- **用行为描述，不用术语评判。** 写"能看懂别人写的类与模板代码"，不要写"中级水平"。术语评判会让学生按面子选。
- **提供"完全没接触过"这一档，并明确它是正常选项。** 没有这一档，学生会往上选。
- **题目里带上项目上下文。** "这个项目用 C++" 比 "你懂 C++ 吗" 更容易让学生准确定位自己。
- **不要问"你想学什么"代替诊断。** 那是定档环节的事，而且初学者说不准自己缺什么——这正是要诊断的原因。
- **学生选"其他"并自由作答时，那是有效信号，认真读。** 他给出的自我描述往往比选项更精确。

## 提问话术

开场必须先说明意图，否则学生会进入"被考试"的状态，后面的回答质量会明显下降：

> "在你开始学之前，我想问你几个问题，摸一下你的基础。**这不是考试**——目的是让我不从你已经会的东西开始讲、也不跳过你不会的。答不出来是完全有用的信息，说明那里要补。"

问完之后，明确给出诊断结论和依据：

> "你的情况是：C 语言基础可以，但没接触过寄存器和外设这一层；构建工具链没问题。所以我建议从第 2 关开始，讲骨架的时候顺带补一次寄存器怎么读写的直觉，不单独开课。"

**给出判断依据**很重要——学生要知道你为什么这样安排。不解释的话，他会怀疑你在敷衍或者灌水。

## 自评复验：校正虚高的档位

**这一步不能省。** 自评选项是定起点的输入，但不是结论。

### 为什么会偏高

三条机制，都是结构性的，不是学生不诚实：

1. **认得出 ≠ 读得懂。** 学生认得出 `for`、`class`、`async` 这些词，就认为自己"会"了。但读懂代码要的是能预判它的行为，这是另一回事。
2. **跟着做过 ≠ 掌握。** "跟着教程走过一遍"的记忆很鲜明，但当时是别人带着走的，独立复现不了。
3. **面子偏差。** 四档选项里选低档像是在承认自己不行。哪怕明确说了不是考试，这个压力依然在。

偏差方向是固定的（偏高），所以校正方向也固定：**往低处校**。

### 出题的两个硬约束

**约束一：题目不能超出你要测的那个档位。** 这是最容易出的错——你想验证 D1（语言），却从项目地图的"值得深挖的点"里挑了一道需要第 5 关知识才能答的题。学生答不上，你按规则降档，于是整条路线被一道超纲题压到了地上。

出题前先自问：**这道题需要的能力，是不是正好等于自评那一档声称的能力？** 不是就换题。

| 自评档位 | 复验题的难度上限 |
|---|---|
| 2（能看懂别人的实现） | 读懂一问一答的直白代码：这段的输入输出是什么 |
| 3（能独立完成） | 读懂带控制流的代码：这个分支什么时候走 |
| 4（能给别人讲清楚） | 才能问"为什么不用更直接的写法"这类取舍题 |

**约束二：一题只测一个维度。** 一道题同时用到语言、工具链和领域知识时，答不上你也不知道该降哪个——结果往往是全降，同样把路线压垮。

### 降档与误判的区分

答不上有两种，处理完全不同：

- **题在范围内，他答不上** → 真的是水平不够，按规则降档
- **题超纲了**（事后发现需要更后面关卡的知识）→ **这是你的错，不是他的**，重出一道范围内的题，不要降档

拿不准时**重出一道更简单的题再问一次**，而不是直接降档。多问一题的代价，远小于把学生的起点定低两档。

### 复验题怎么出

用项目真实代码出 1–2 道，问他**能立刻回答、或立刻答不上来**的问题，不要出需要想五分钟的题。好题有三个特征：

- 答案只有对/错/说不清，不需要长篇论述
- 用得到自评那个档位所声称的能力
- 答错不丢脸（设计成"这道题本来就需要额外知识"）

| 自评声称 | 复验题（换成项目真实内容） |
|---|---|
| 能看懂别人的 Python 代码 | 指一段 10 行的真实函数："这段的输入是什么，输出是什么？" |
| 能独立编译项目 | "要改这个开关，你要动哪个文件、跑哪条命令？" |
| 懂这个领域的基本概念 | 指项目里一处领域概念："这一步在算什么？为什么需要它？" |
| 读过上万行的多模块项目 | "这个功能要改，你会先打开哪个文件？" |

注意最后一列都停在**该档位声称的能力**上，没有往上升到"为什么不用别的写法"——那是第 4 档才该问的（见上一节的难度上限表）。

### 校正规则

| 复验结果 | 处理 |
|---|---|
| 全部答上，表述准确 | 自评可信，按原档位定起点 |
| 答上一半 / 表述含糊 | 自评**降一档** |
| 基本答不上 | 自评**降两档**，并考虑先补前置 |
| 意外答得很好（超出自评） | **升档**，并明确告诉他"你的实际水平比自评高，我们从更高的地方开始" |

降档后必须说理由，且理由要指向**题目**而不是他这个人：

> "这道题实际需要先知道 `extern` 声明和定义的区别，我们把这个补上再往下走。"

不要说"你基础比你自己想的差"——同一件事，两种说法，后者会让他之后开始掩饰不懂，你就拿不到真实信号了。

### 前置补课的通关题模板

复验显示需要先补前置时，**前置讲完也要过关**，不能直接放行。前置通关题的形式：

1. **让他在真实代码上指出**，而不是背书：例如"在这个文件里，哪一行是声明、哪一行是定义？"
2. **让他做一次微小预测**："如果我把这里改成 X，你预测输出会怎么变？"
3. **让他复述因果关系**："为什么必须先做 A 才能做 B？"

三条里过两条即可进入正关。**一条都过不了就不要往下走**——前置没补上，后面每一关都会卡在同一个地方，而且他会以为是后面的内容太难。

## 答案到起点的映射

先看四档的对策，再看组合：

### 单维度映射

| 维度 | 档位 | 起点调整 |
|---|---|---|
| D1 语言 | 1–2 | **必须先补**：用项目里的真实代码当教材，讲 20–40 分钟语言要点，再进关卡 1 |
| D1 语言 | 3 | 正常从关卡 1 开始；讲解时对语言特性随手解释 |
| D1 语言 | 4 | 正常从关卡 1 开始；可以更快，语言层面不必停留 |
| D2 工具链 | 1–2 | **必须先补**：带他跑通一次构建与运行。跑不起来就没法验证理解 |
| D2 工具链 | 3–4 | 正常进行；第 6 关可以要求他自己跑并解释输出 |
| D3 领域 | 1–2 | 从关卡 1 开始，但**第 1 关多花时间**：先讲清领域要解决什么问题 |
| D3 领域 | 3–4 | 正常进行；第 5 关可以直接讨论工程取舍 |
| D4 阅读 | 1–2 | **把每关拆得更细**：关卡 3、4 各拆成 2–3 小步，每步都画图 |
| D4 阅读 | 3–4 | 正常进行；可以用"你先自己追一遍，我来看你追对没有"的方式 |

### 组合规则

1. **硬门槛优先。** D1 或 D2 是 1–2 档时，不管其他维度多好，都先补硬门槛。理由很直接：不会语言或跑不起来，后面的每一关都会卡。
2. **缺口跨多维度时从最低处开始**，并说明为什么先补它。学生要知道这个取舍。
3. **全部是 3–4 档时不要省掉关卡 1。** 熟练的读者最容易跳过"这项目为什么存在"，结果在第 5 关讨论取舍时发现根基是空的。
4. **全部是 4 档时，改用检验式开场**：请他先自己讲一遍这个项目的大致结构，你听着找偏差。承认他已经越过了前面几关——但要用他的复述来验证，不要凭选项就放过。

## 定深度：了解框架 vs 深入研究

**必须让学生选，不要替他决定。** 学习深度直接决定他要投入多少时间，这是他的决定。

### 提问模板

```
问：这次学习你想达到什么程度？
○ 了解框架：知道项目由哪些部分组成、大致怎么跑、改动会牵动什么就行
○ 深入研究：要读懂关键实现，能自己定位和修改代码，能判断改动的后果
○ 先了解框架，之后可能再深挖（推荐给第一次接触这个项目的同学）
```

第三个选项是在"拿不定主意"时最稳的路径，值得作为推荐项给出：先建立全局再决定深挖哪里。反过来（一头扎进某个模块再回头看全局）是初学者最常迷路的方式。

### 两档的差别

| | 了解框架 | 深入研究 |
|---|---|---|
| 终点 | 第 4 关 | 第 6 关 |
| 每关深度 | 能说出"这里有个做 X 的环节，在 A 文件" | 能说出"它是怎么做的，为什么这么做" |
| 对代码的态度 | 读关键行，跳过实现细节 | 逐行读核心实现，含边界条件 |
| 提问方式 | "这部分做什么？" | "如果这里改成 Y 会怎样？" |
| 测试要求 | 无 | 必须有所收获，能解释现象 |
| 典型时长 | 1–2 次会话 | 多次会话，且会分模块多轮 |

**"了解框架"不是低配版。** 它是绝大多数工程场景下真正需要的深度：你要在别人的代码上加功能，先要知道全局在哪、边界在哪。明确跟学生说这句话，避免他觉得自己选了"简配"。

### 档位可以在中途改

学到一半发现"其实我想深挖这块"或"我只要大概知道"，**随时允许调整**，并在 `progress.md` 里记下变更和原因。路线是服务学生的，不是反过来。

## 诊断错了怎么办

诊断是自评，必然有偏差。**在关卡 3 之前的任何卡顿，第一反应都应该是"是不是起点定高了"，而不是"学生不认真"。**

识别信号：

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 学生反复问"这个函数是什么意思" | D1 实际低于自评 | 停下补语言，用真实代码当教材 |
| 学生说"我大概懂了"但复述不出来 | 起点高了或拆得不够细 | 把关卡拆成更小的步 |
| 学生问的问题都超出当前关卡 | 起点定低了 | 提速，或直接跳到下一关 |
| 学生沉默 / 只回"嗯" | 题目太大，或怕说错 | 换成更小的具体问题，并强调答错无害 |

**当场承认并调整，不要硬撑。** "我判断你的起点定低了，我们跳一关" 比让他在已经懂的内容上耗一个小时好得多。

## 常见坑

- **用通用题库。** 问"你懂不懂面向对象"这种与项目无关的问题是浪费——哪怕答了，你也无法据此定起点。
- **一次问 8 个问题。** 工具上限 4 个；超出的用后续自然对话补，不要连发两轮问卷。
- **让学生自己选起点关卡。** 他不知道自己缺什么，这正是诊断的目的。选项只用来描述水平，路线由你根据映射定。
- **选项写成对错题。** "你熟悉卡尔曼滤波吗：熟悉 / 不熟悉" —— 学生只会选"熟悉"。
- **不问 D4。** 阅读经验是决定"每关拆多细"的唯一依据，跳过它会导致把初学者一次喂太多。
- **诊断完不说结论。** 学生付出了回答成本，必须拿到结论和依据，否则下一次他就不认真答了。
- **把诊断当一次性动作。** 后面每次会话的轻量复检（"上次那部分现在还有印象吗"）是诊断的延续。
